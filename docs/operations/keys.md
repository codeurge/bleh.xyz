# Keys and secrets

Every key and secret the deployment uses, how it is generated, where it
lives, how it is rotated and revoked. Signing formats: observation-v0 § 7
and [manifest-v0](../specs/manifest-v0.md) (secp256k1, EIP-191, verifiable
with `ecrecover`). Nothing in this list is ever committed; `scripts/check.sh`
scans for key-like strings.

## Inventory

## Why block-signing keys are hot

A Merkle root is signed per block per stream, several times per block, and
Hyperliquid produces many blocks per second. A cloud KMS call adds a network
round trip (tens of milliseconds) to the 50 ms budget and costs per request
(millions of requests a month), and a hardware module on the node box is a
single point of failure. So block-signing keys are software keys on the node
box, with a short validity, one per ingest path, and their authority comes
from an attestation signed by the root identity key. A stolen block key
signs for at most its validity window and is revoked by publishing a
revocation (below). The manifest key, used daily, does sit in hardware.

## Generate a key

On an offline or trusted machine:

```bash
# 32-byte secp256k1 secret as hex (the format the services read).
umask 077
openssl ecparam -name secp256k1 -genkey -noout -outform DER \
  | tail -c +8 | head -c 32 | od -An -tx1 | tr -d ' \n' > signing-key.hex

# Or generate and print the address in one step with the archive tool
# (same key format; never overwrites, mode 600):
docker run --rm -v "$PWD:/k" -w /k bleh/archive manifest keygen --out new-key.hex

# The Ethereum address of an existing key:
cast wallet address --private-key "0x$(cat signing-key.hex)"     # Foundry
```

`deploy/up.sh synthetic` generates throwaway keys this way for local use
only; production profiles refuse to start without keys you installed.

### Hardware and KMS paths

| Option | Supports secp256k1 signing | Fits |
|---|---|---|
| YubiHSM 2 (USB, on the home-archive server) | Yes (ECDSA on secp256k1) | Manifest key; the archive signs through its connector |
| AWS KMS asymmetric key, spec `ECC_SECG_P256K1` | Yes | Manifest key in Tier 3, or when the home server is unavailable; the signature needs the recovery id computed client-side for EIP-191 |
| Hardware wallet (Ledger, Trezor) | Yes, with EIP-191 personal-sign | Root identity key, used by a person |
| File plus sops/age encryption in a private operations repository | — | Backup copies of hot keys; never the only copy of the root key |

The archive reads `BLEH_ARCHIVE_SIGNING_KEY_FILE` today; a KMS or HSM
signer is an archive-lane change behind the same interface.

## Publish signer addresses

Clients and relays accept a signature only from a published address.

1. **Gateway `hello`.** `signers` lists the active block-signing addresses
   (protocol § 1). Relays are configured with the same list
   (`BLEH_SIGNER_1`, `BLEH_SIGNER_2`, passed as `--signer`) and drop
   anything else.
2. **Signed key list.** `https://data.bleh.xyz/keys/signers.json`, signed
   with the root identity key: per key the address, role (`block`,
   `manifest`, `anchor`), ingest path, `valid_from`, `valid_until`,
   `status` (`active`, `retired`, `revoked`) and, for revoked keys,
   `compromised_from` (block number and time).
3. **On-chain registry (Phase 2).** An attestation per key (for example the
   Ethereum Attestation Service), issued by the root identity address, so
   the list survives the loss of every domain.
4. **Documentation.** The current addresses in the project README once
   live.

## Rotate

Block-signing key for path `a`:

1. Generate the new key; compute its address.
2. Publish it as `active` with `valid_from` a few hours ahead, in
   `signers.json` and the registry, signed by the root key.
3. Install `secrets/signing-key.hex` on the node box and restart the reader
   (`deploy/up.sh node-box restart hl-node-reader`) after `valid_from`.
4. Mark the old key `retired` with `valid_until` set to the switch time.
   Records it signed stay verifiable for that window.
5. Update `BLEH_SIGNER_1`/`_2` on the relays (keep the old address as the
   second signer until the switch is done).

The manifest key rotates the same way, with the next manifest signed by the
new key and the old key retired after it. Tokens and API keys: create the
new one, install it, restart the consumer, delete the old one.

## Revoke (compromise)

1. Stop the affected signer: `deploy/up.sh node-box stop hl-node-reader`
   (for the manifest key: `systemctl disable --now bleh-archive-daily.timer`).
2. Publish a revocation: `status: revoked` and `compromised_from` (the
   earliest block or time the key could have been misused) in
   `signers.json` and the registry. Clients reject signatures by that key
   from `compromised_from` on.
3. Generate and publish a replacement (rotation steps 1–5, without the
   overlap), and restart.
4. Re-check the compromise window: compare that path's records with the
   other path (Tier 2+) or with Hyperliquid's public archive, and issue
   corrected manifests if any published data was affected (correction
   protocol: new versions, old hashes stay listed).
5. Rotate every secret that lived on the same host.

Full incident steps: [incident.md](incident.md#key-compromise).

## TLS certificates

| Hostname | Certificate | Renewal |
|---|---|---|
| `live`, `api`, `data`, tunnel hostnames at the Cloudflare edge | Cloudflare edge certificates | Automatic |
| `live`, `api` on each relay (origin side, SSL mode Full (strict)) | Cloudflare Origin CA certificate from the edge stack (`origin_cert_pem`, `origin_key_pem` outputs), or from the dashboard so the key never enters Terraform state | 15 years; replace on compromise |
| `relay-N` (direct, DNS-only) | Let's Encrypt via Caddy (HTTP-01 on port 80) | Automatic; `BlehCertificateExpiring` watches it |
| Node box and home server | None: the gateway is reached over the overlay, Grafana through the tunnel | — |

Install the Origin CA files on a relay:

```bash
cd deploy/terraform/envs/edge
terraform output -raw origin_cert_pem > origin.pem
terraform output -raw origin_key_pem > origin-key.pem
scp origin.pem origin-key.pem ops@relay-1:/opt/bleh/src/deploy/compose/secrets/origin-ca/
shred -u origin.pem origin-key.pem
```

## Signing failures

`BlehSigningFailures`: a service could not sign. Check that the key file is
present, non-empty and readable by UID 65532 inside the container
(`docker compose exec hl-node-reader ls -l /run/secrets/`), that it holds 64
hex characters, and for an HSM or KMS signer that the device or credentials
are reachable. Unsigned blocks are not published as signed; clients see the
commitments missing and can verify later from the archive.

## Operational secrets

- Hosts: `deploy/compose/.env` (0600) and `deploy/compose/secrets/` (0700),
  both git-ignored; systemd alternatives read `/etc/bleh/*.env` (0600) and
  `/etc/bleh/secrets/`.
- Terraform state holds the tunnel token and the Origin CA
  key: keep it in the private state bucket (`deploy/terraform/backend.example.hcl`)
  and limit that token to operators.
- CI: registry access uses the workflow's own token; the deploy SSH key and
  known hosts are GitHub environment secrets behind required reviewers.
- Backups: an encrypted copy (sops with age recipients held by two
  operators) of `.env` and `secrets/` for each host, in a private
  repository or offline storage.

## Provider credentials

Terraform reads credentials only from the operator's environment:
`CLOUDFLARE_API_TOKEN` (edge; scoped to the zone, R2, Tunnel and Access),
`~/.oci/config` (relays-oci), `HCLOUD_TOKEN` (relays-hcloud), `AWS_PROFILE`
(tokyo, fallback-dns, and the R2 state bucket via `AWS_ACCESS_KEY_ID` /
`AWS_SECRET_ACCESS_KEY`), `VULTR_API_KEY` (tokyo).
